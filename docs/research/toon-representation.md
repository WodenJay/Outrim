# TOON 作为入口表示：收益基线、保真边界与验证候选

辅助材料，服务于 [决定内容分类、压缩策略与算法验证 #5](https://github.com/WodenJay/Outrim/issues/5)。本文不实现产品，不替用户决定默认格式或依赖。

## 结论

**TOON 符合“尽量保留内容、通过改变表示减少 Token”的候选方向，但不是所有 JSON 都应转换，也不是完整 JSON 原文的逐字节无损编码。** 其价值不能只用相对带缩进 JSON 的节省率证明；必须同时看实际输入、紧凑 JSON、适用的表格表示以及模型使用质量。

- 官方基准中，平坦数据集的 TOON 比紧凑 JSON 少约 **35.2%** Token；混合结构数据集的 TOON 总量反而多约 **1.6%**。这说明有选择地使用值得验证，不说明所有平坦输入必定受益或所有嵌套输入必定变差。
- CSV 在纯表格数据上可能更小，但普通 CSV 并不自动表达 JSON 的全部类型、空值和嵌套语义，不能不加限定就当成同等保真的通用替代。
- 格式保真、具体解析/编码实现的保真、模型理解与任务质量，是三件不同的事。本轮没有做模型理解或真实任务实验。
- Rust 有现成实现可考察，不代表已决定采用；轻量嵌入时需注意其默认 CLI feature。

## 2. 基线决定如何解释节省

官方 Token Efficiency 使用 `gpt-tokenizer / o200k_base`：

| 数据集轨道 | 带 2 空格缩进的 JSON | 紧凑 JSON | TOON | CSV |
|---|---:|---:|---:|---:|
| Mixed-Structure | 393,637 | 260,451 | 264,734 | 不作通用比较 |
| Flat-Only | 164,643 | 104,908 | 68,030 | 64,247 |

由此可得：

- Mixed-Structure：TOON 对带缩进 JSON 少 32.7%，但对紧凑 JSON **多 1.6%**。
- Flat-Only：TOON 对紧凑 JSON **少 35.2%**，但比该轨道 CSV **多 5.9%**。
- 同一混合轨道中也有 TOON 获益的数据集，不能从汇总值推导某个输入一定不适用。

官网另一处“少 42.6% Token”的主张使用带缩进 JSON 作基线，不等于相对紧凑 JSON 的收益，也不等于 Outrim 的产品收益。

对 Outrim 应分别计算：

1. **原始工具文本 → 最终替换文本**：用户实际得到的入口减少量，包含说明、路径等新增文本。
2. **紧凑 JSON → 候选表示**：格式转换相对简单已有基线的额外价值。
3. **完整任务**：恢复、额外轮次、任务质量、总用量与耗时。前两项不能证明第三项。

纯表格时可以加入 CSV/TSV 对照；若类型或嵌套需要额外说明，其成本也应计入。`{"fields":[...],"rows":[[...]]}` 是另一种保留字段名、值及位置映射的候选。**没有字段清单的行数组会丢字段名，不能冒充等价对照。**

## 3. “信息不变”需要检查哪一层

### 3.1 原始文本不等于解码后的值

例如，官方示例中的：

```json
{"users":[{"id":1,"name":"Ada","role":"admin"},{"id":2,"name":"Bob","role":"user"}]}
```

可表示为：

```toon
users[2]{id,name,role}:
  1,Ada,admin
  2,Bob,user
```

它保留字段与值的对应关系，不需要每行重复键名。但这不意味着可从 TOON 恢复原 JSON 的空白、转义字面量或对象键的原始排列；数字规范化也可能改变书写形式。

应分开检查：

- **原文/字节一致**：Outrim 保存的入口原文负责保留，不指望转换格式还原字节。
- **选定数据模型下的值一致**：类型、精确数值、字符串内容、数组顺序、字段对应关系等，需明确检查边界。
- **Agent 使用质量不受明显损害**：模型能否正确理解并完成任务，必须实测。

有原文并不能把错误数值、缺字段或类型变化自动变成“无损”；它们仍应算候选变换失败或有损处理，而不是表示等价。

### 3.2 具体 Rust 管线的数值风险

`toon-format 0.7.0` 的内部数值类型为 `PosInt(u64) / NegInt(i64) / Float(f64)`。`src/types/value.rs:426-455` 的 `From<serde_json::Value>` 对数值依次尝试 `as_i64()`、`as_u64()`、`as_f64()`，均不成功则生成 `Null`。它不是任意精度十进制模型。

研究探针使用两种配置：

- 默认 `serde_json`：超出整数域的数可能先转为浮点近似；`1e400` 在解析阶段报 `number out of range`，并非 TOON 规定把它改为 null。
- `serde_json` 开 `arbitrary_precision`：上游可以保留更大数字，但后续转换到该 crate 的内部模型仍可能近似或落到 null。上游选项不能独自保证整条管线保真。

这些是**实现与配置的边界**，不能推广成 TOON 格式必然损坏所有大数，也不能因为普通样本往返相等就宣布任意 JSON 安全。具体探针未纳入仓库，边界处理仍需开发阶段固化测试；本轮主代理核对了内部数值域及上述转换分支，未重跑完整数值矩阵。

其他需检查的输入包括重复键、特殊 Unicode、看似布尔/数字的字符串、缺字段与显式 null、含分隔符或换行的字符串、深度上限。配置内容和源码字符串不因外层是 JSON 就可以被改写其内部内容。

## 4. Rust 实现可用性：仅作为候选评估

本机核对的 `toon-format 0.7.0 / Cargo.toml`：

- 许可证为 MIT。
- `default = ["cli"]`。
- `cli` 启用 clap、ratatui、crossterm、arboard、syntect、tiktoken-rs 等 CLI/TUI 相关可选依赖。
- 如选择库嵌入，应考察 `default-features = false`，避免因仅需编码器而引入默认 CLI 栈。
- 关闭默认 feature 后仍有 serde、serde_json、indexmap、thiserror 等依赖；完整传递树与许可证须按实际 lockfile 检查，本文不承诺固定包数或全部采用同一许可证。

该库可产生 TOON 文本，不意味着会替 Outrim 判断输出是否更小、是否适合当前模型、或这次转换是否值得。

字符减少不是 Token 减少的保证；结构特征也不是保证。运行时采用什么低成本判断方式、离线如何用目标词表校验，仍待产品方案决定，不能把“研究中使用 tokenizer”直接变成必须增加运行时 tokenizer 的要求。

## 5. 模型说明与实验范围

官方提供格式标签、小例子和说明建议，但本轮**没有验证**：

- 不增加说明时模型是否已经能正确读懂。
- 一行标签、少量例子或完整说明对质量有多少改善。
- 增加说明后，短输出是否仍有收益。

因此不要一开始就强加教程或修改 system prompt。可先比较不额外说明的候选；确有理解问题时，再把必要的最小说明作为独立变量。说明、包装与路径等必须计入候选的完整体量，不能只统计数据体。

官方 retrieval benchmark 不是 Outrim 的真实 Agent 任务，本轮未复现其质量实验。工具调用参数生成或并行调用协议的研究也不能直接替代工具结果入口压缩的验证；本报告不据此提出修改工具 schema、调用参数或恢复工具的方案。

## 6. 建议的候选与验证（待用户选择）

建议将 **TOON 与紧凑 JSON、字段清单 + 行数据放在同一组候选中比较**，而不是预先指定所有 JSON 一律 TOON。对适用的纯表格数据可加 CSV/TSV，但需检查是否保留所需类型与结构。

最小验证分三层：

1. **保真**：明确字段、类型、精确值、对应关系与顺序的要求；不能只靠已规范化宿主值的 `==` 断言原输入没损失。
2. **局部收益**：最终完整文本相对原始输入与简单基线的字符量、目标词表 Token、转换耗时。收益不足时不为覆盖率强行转换。
3. **任务效果**：读取字段、比较记录、判断条件等真实使用任务的正确性、恢复、轮次与全任务成本。没有测量就不宣布某格式默认有效。

重复记录的游程表示、公共字段提取等是其他候选，不是 TOON 自动完成的能力；若要探索，必须保留次数、顺序与对应关系，不能把删除重复记录假装无损。本文不建议因此改动受保护的源码/配置。

## 7. 复核与撤回首版过强表述

初稿为提交 `490337ed1ab34c0dea2878d782984b119c831c3c`。主代理复核后，本修订明确：

- “TOON 不能带来信息基本不变且更省 Token”不成立；它是有条件成立、值得比较的表示候选。
- “官方数字对紧凑 JSON 是负收益”只适用于所引混合轨道的汇总，不能覆盖平坦轨道。
- “最小基线不是 JSON 而是 CSV”忽略类型、嵌套与说明成本，不作通用结论。
- 初稿声称 `serde_json::Value ==` 在有序 map 下必然因键序变化而不等，依据不足：本机 `indexmap 2.14.2/src/map.rs:1842-1857` 的 `PartialEq` 按键查值比较，不比较迭代顺序。值比较不能代替原键序或原字节比较。
- 不沿用仅保存在临时目录、未独立固化的合成样本总量作为产品阈值，不把特定输入的压缩率推广成普遍收益。

研究的落点是：**先按保真与任务效果筛选，再判断哪种表示确实值得采用；不因 TOON 的宣传数字直接全量替换，也不因部分输入变贵就把它排除。**
